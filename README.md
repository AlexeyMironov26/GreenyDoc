Представлен проект, состоящий из бэкэнда, фронтэнда и использования api нейросети, 
Данный проект используется для анализа листьев растений по фото и определения их заболевания
Для начала вам нужно запустить фастапи сервер (бэк) с помощью python main.py
Потом из папки react запустить фронт, написанный на реакте с помощью npm run dev
И перейти по ссылке, данную вам после запуска фронта в консоли
Там и будет наш сайт GreenyDoc. Где вам для начала нужно совершить регистрацию или авторизоваться
После этого вы сможете перетаскивать изображения листьев в специальную рамочку или выбирать их файлы из проводника 
И, нажимая, на кнопку анализировать получать либо диагноз, либо уведомление о том, что болезни не обнаружено
Либо уведомление о том, что растения не обнаружено







Справка по устройству програмистских концепций проекта:

Access (30 min) & Refresh (7 days) Tokens
access токен - это токен, который используется для авторизации пользователя (если в запросе найден токен действующий, то доступ пользователю к его учётной записи будет автоматически предоставлен без ввода логина и пароля), refresh token как и acccess token присваивается пользователю при авторизации. Если у пользователя истёк access token, но остался refresh, то при запросе с клиента с рефреш токеном валидным на сервер, сервер выдаст новый access token клиенту и предоставит доступ, а вот если уже refresh токен истечёт, то нужно заново авторизовываться. 

смысл в том, что у нас благодаря такой системе предоставляется долгосрочный доступ пользователя к своей учётной записи после авторизации, но в то же время токен, с помощью которого доступ осуществляется, обновляется раз в небольшой интервал времени, из за чего, даже если им завладеет злоумышленник, автономное обновление токена быстро прервёт его сессию. Постоянный же рефреш токен, который и обновляет наш access token интервально лежит в надёжном месте и его сложнее украсть. Но в таком случае возникает вопрос, почему бы не использовать refresh token для проверки пользователя всегда, зачем использовать access token, лежащий в менее безопасном месте? по следующим причинам: это менее безопасное место более доступно нам и мы можем из него гораздо быстрее доставать access токен, разгружая систему, при верификации пользователя, сам факт, что refresh token отправляется гораздо реже, чем access tokens различные, делает вероятность того, что его украдут в разы меньше, а понижать эту вероятность максимально критично, потому что урон от компрометации refresh токена будет несравнимо больше, чем от компрометации access токена. Схема refresh-access это компромисс между безопасностью и доступностью/быстротой. 
1. Логин:
   Клиент → Сервер: логин/пароль
   Сервер → Клиент: access_token (15 мин) + refresh_token (7 дней)

2. Обычный запрос:
   Клиент → Сервер: access_token в заголовке
   Сервер проверяет access_token → возвращает данные

3. Access токен истек:
   Клиент → Сервер: refresh_token на /api/auth/refresh
   Сервер → Клиент: новый access_token

4. Logout:
   Клиент → Сервер: refresh_token
   Сервер удаляет refresh_token из БД → сессия завершена

Ключевые эндпойнты для refresh+acccess
/register — регистрация + авто-логин с выдачей refresh+access tokens;

/login — вход с токенами;

/refresh — обновление access token через refresh;

/logout — отзыв refresh token;

/delete-account — отзыв сессий + удаление.

SEO (Search Engine Optimization) — это комплекс мер для улучшения видимости сайта в поисковых системах (Google, Яндекс).

Техническое SEO — скорость загрузки, индексация, robots.txt, sitemap.xml

Контентное SEO — мета-теги (title, description), заголовки (h1-h3), alt для изображений

SEO-оптимизация:
Это комплекс мер, чтобы робот поисковика (Googlebot, Яндекс.Робот) мог:

✅ Найти сайт (sitemap.xml, robots.txt)

✅ Прочитать содержимое (мета-теги, заголовки, alt)

✅ Понять структуру (человекопонятные URL)

✅ Оценить качество (быстрая загрузка, уникальный контент)

robots.txt — инструкция для поисковых роботов
Что это: Файл в корне сайта, который говорит поисковым роботам (Google, Яндекс), какие страницы можно сканировать, а какие нельзя.
Зачем нужен:

✅ Скрыть от индексации служебные страницы (логин, настройки, API)

✅ Указать роботам, где находится sitemap

✅ Экономить краулинговый бюджет (чтобы роботы не тратили время на ненужные страницы)

2. sitemap.xml — карта сайта для поисковиков
Что это: XML-файл, который перечисляет все важные страницы сайта, которые должны быть проиндексированы.
Зачем нужен:

✅ Помогает поисковикам найти все важные страницы

✅ Указывает приоритет и частоту обновления

✅ Улучшает индексацию сайта

Индексация - сканирование сайта специальным роботом поисковика и занесение его в поисковой склад, благодаря чему сайт потом можно найти в поисковике.

HelmetProvider предоставляет возможность динамически изменять мета-теги в реакт

Мета-теги — это специальные HTML-теги, которые располагаются в <head> документа. Они не видны пользователям, но важны для поисковых систем и социальных сетей.

SEO.tsx — это мозг SEO на фронтенде. Без него поисковики:
Не увидят заголовки и описания
Не поймут, что индексировать, а что нет
Не смогут показать красивые превью в соцсетях
Он не дублирует robots.txt и sitemap.xml — они про разное:
robots.txt/sitemap.xml — техническое SEO (что сканировать)
SEO.tsx — контентное SEO (как это показать в выдаче) 

JsonLd.tsx -
Этот компонент добавляет структурированные данные (JSON-LD) на страницу — специальную разметку, которая помогает поисковикам понять смысл контента.

 alt - это надпись, которая будет отображаться, если изображение не прогрузилось? что seo файл позволяет изменяя мета-теги в нём изменять их и во всех элементах разметки, где используется этот seo-элемент, это и называется динамическое изменение мета-тегов (seo файл элемент создаёт структуру, в которую оборачивается все штуки, используемые в нём -фабрика мета -тегов)? что seo файл и jsonld файл отвечают за наполнение разметки фронтенда мета-тегами, доступными для чтения роботу, а также делает возможным красивые превью-надписи в различных мессенджерах и поисковиках, а jsonld предоставляет роботу смысловую информацию о сайте.

ТЕСТИРОВАНИЕ
Модульные тесты проверяют отдельные маленькие функции в изоляции (например, hash_password() или validate_file()), не трогая базу данных, сеть или сервер — они быстрые и не требуют запуска приложения. Интеграционные тесты проверяют, как несколько компонентов работают вместе (например, endpoint → БД → ответ или frontend-компонент → API → отображение), используют тестовую БД, реальные запросы через TestClient и моки для внешних сервисов — они медленнее, но показывают, что вся связка функционирует корректно.
